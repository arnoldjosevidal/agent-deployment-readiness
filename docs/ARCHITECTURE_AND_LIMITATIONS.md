# Architecture and limits

User/task context → model proposal → common strict schema parser → A bypass or independent G policy → simulated tool runtime → linked evidence journal → evaluator → separate comparison channels.

- `adr_gateb`: S1 selection, A/G runner, strict arguments, independent policy, chronological proof and evaluator channels.
- `adr_g64r`: durable SQLite source of record, trace/CSV views, linked events and recovery.
- `adr_p1`: finite Nebius request reservation, explicit authorization and hard child-process deadline; no hidden SDK retries.
- `adr_live`: exact two-case interface and local full-payload token counter; provider binding remains unverified.
- `demo`: static offline walkthrough with synthetic fixture evidence and historical summaries, not a live model client.
- `adr_approval`: loopback-only approval service. Its default workflow routes `ScriptedModel` fixture proposals through the unchanged candidate policy and resumes after authenticated approval or rejection. V2 also includes a separately activated `EXPLORATORY_LIVE_NON_B1` adapter for Nem 점ius/NVIDIA that preserves the policy and simulated tools; its final distribution code was tested only against loopback provider mocks.

The G policy has no evaluator ground_truth input. Both arms share common parsing and resource caps. ALLOW may execute, BLOCK and REQUIRE_APPROVAL do not. Infrastructure failure means null/stop, not an attacker failure. Native and candidate evaluator metrics must not be pooled. Stored checksums are local integrity checks, not protection against an administrator rewriting all authorities.

Current limitations: B1 unresolved and the protocol-confirming S1 result is not run; historical G6.3 used oracle policies. The offline flow uses predetermined scripted tool proposals and is not Nemotron inference. The V2 source commit completed one two-request exploratory calendar smoke; it does not establish calendar accuracy, prompt-injection resistance, B1, or production readiness. The local single-operator password is not enterprise identity, and the loopback service is not production-ready; Python network denial is not OS isolation; no generalized efficacy or deployment-readiness claim is made. `store:false` does not establish zero retention. Synthetic benchmark data and no real external tool effects are the approved scope. S2 stays sealed.
